======================================================================
1. WHAT NEXUSOPS IS
======================================================================
NexusOps is a CLI-first, configuration-driven AWS DevOps automation tool
written in Python. A single YAML file (nexusops.yaml) drives Terraform,
Docker, AWS ECR, and Kubernetes. It validates the configuration before
acting, keeps planning separate from deployment, and requires explicit
typed confirmation before touching AWS.

Workflow:
  nexusops.yaml
    -> validate
    -> generate      (terraform.tfvars.json)
    -> plan          (saved plan + freshness manifest)
    -> apply         (requires typing APPLY)
    -> build-image   (local Docker image)
    -> push-ecr      (requires typing PUSH)
    -> render-k8s    (Kubernetes Deployment + Service)

======================================================================
2. COMPONENTS
======================================================================
CLI (run_nexusops.py) - the single authoritative entry point
  validate     Validates application, AWS, S3, ECR, container, and
               replica settings.
  generate     Writes Terraform input variables.
  plan         terraform init/validate/plan; saves the plan plus a
               SHA-256 manifest of all inputs (YAML, tfvars, *.tf,
               auto-loaded *.tfvars, provider lock file, plan file).
  show-plan    Displays the saved plan; rejects stale/missing plans.
  apply        Shows the exact saved plan, requires typing APPLY,
               re-checks freshness after confirmation, then applies.
  build-image  Builds the Docker image locally. Never pushes.
  push-ecr     Pushes to an existing ECR repo after typing PUSH.
  render-k8s   Generates hardened Kubernetes manifests from the YAML
               into build/kubernetes/manifests.yaml (gitignored).

Infrastructure (infrastructure/, Terraform, AWS provider ~> 6.0)
  - Optional S3 bucket: full public access block, BucketOwnerEnforced
    (ACLs disabled), AES256 default encryption.
  - Optional ECR repository: immutable tags, scan on push, AES256
    encryption, force_delete = false.
  - Provider lock file contains checksums for Windows and Linux.

Application (app/backend/)
  - FastAPI service with GET /health -> {"status":"ok"}.
  - Dockerfile: python:3.12-slim, non-root user 10001, HEALTHCHECK.
  - docker-compose.yml for local runs.

Kubernetes (generated by render-k8s)
  - Deployment: replicas from deployment.replicas (1-20), readiness and
    liveness probes on /health, CPU/memory requests and limits,
    non-root UID 10001, no privilege escalation, all capabilities
    dropped, read-only root filesystem (emptyDir at /tmp), RuntimeDefault
    seccomp, no service-account token, imagePullPolicy IfNotPresent.
  - ClusterIP Service on port 80 -> container port 8000.

CI (.github/workflows/ci.yml, GitHub Actions) - four jobs:
  1. Python      compileall, 46 unit tests, validate, generate.
  2. Terraform   fmt -check, init (read-only lock file), validate.
  3. Docker      build image, run container, check /health and Docker
                 HEALTHCHECK; Trivy image scan; Trivy config scan of
                 Terraform, Dockerfile, Compose, and Kubernetes manifests.
  4. Kubernetes  ephemeral kind cluster; deploy rendered manifests;
                 verify rollout, ready replicas == configured replicas,
                 and /health through the Service.

======================================================================
3. SAFETY CONTROLS
======================================================================
  - CI has read-only repo permissions and no secrets or AWS credentials.
  - Unit tests fail if CI ever adds plan, apply, destroy, push-ecr,
    docker login/push, or kubectl commands not targeting the kind cluster.
  - Trivy 0.76.1, kind v0.33.0, kubectl v1.37.0 are SHA-256 verified;
    the kind node image is pinned by digest.
  - Terraform state, plans, manifests, generated tfvars, credentials,
    and the virtual environment are gitignored.
  - Accepted risk documented in .trivyignore: AWS-0132 (demo S3 bucket
    uses SSE-S3/AES256 instead of a paid KMS customer-managed key).
